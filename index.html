Core features

Structured semantics, and a living graph engine

Markdown is a good format for people to write in. As the memory and the documentation behind an agent it runs into the problems on the next page. To get past them the system stops organising content by files -- the store is still files, but a file boundary no longer decides what is read, what is written, or what is run -- and rebuilds how knowledge is organised, handed out and computed on. Six things.

01

A minimal query surface for agents

A compact interface built for machine reading and for a token budget, with rendering markup left out entirely. outline, search, refs, batch and the other verbs answer in S-expressions, one item per line, and an agent can see the size of what it is about to read before it reads it. There is no second, prettier output mode to parse.

$ theourgia outline --depth 1
- 8pniyrtk.j  Home
- 8pniyrtk.k  Why not markdown
- 8pniyrtk.l  Model

$ theourgia search "stale-baseline"
(hit "8pniyrtk.2l" 4 "refusal, stale-baseline, commit, example, answer")
(hit "8pniyrtk.1b" 1 "A refused commit does not simply say no. It answers stale-baseline, and it names")
02

One graph across artifacts and languages

The wall between the code repository and the document store is a filesystem accident, not a property of the knowledge. Everything engineering produces goes into one graph. A section of a design, a Scheme macro, a function in another language and a decision record are all blocks -- equal, each with its own id, each addressable on its own. Edges are typed and directed, so a requirement can point at the code that meets it, the code at the test that checks it, and the test back at the discussion that decided it.

A name is a block

In a Scheme library block this is literal rather than a metaphor. A definition is a block, and evaluating an expression against that library is evaluating the definitions those blocks hold -- so a name resolves to its definition block, log <id> gives that definition's history, and an explicit edge ties it to the design that motivated it. The same three questions about one name -- what it is, how it got that way, why it exists -- are three reads rather than three searches.

Other languages, more modestly

Source in other languages goes in as text blocks cut at top-level regions, with names extracted as well as the language table allows. They are blocks like any other: addressable, linkable, with their own history. What they do not get is the resolution above -- a name in Python source is not a binding the store can follow to a block.

03

Global backlinks at almost no cost

This changes how an agent, or a person, looks for context, and it changes what that costs. refs <id> is one small query that answers the whole picture at once: which design mentions this function, which prose block refers to it -- and log <id> gives the history of the block itself. search finds the block that answers, and the agent reads that block instead of the document around it. Measured on 56 questions over 20 real documents: search, then read the block that answers, cost 15% of the tokens that reading the whole document each time would have; outline, then read, 20%. The outline of an entire corpus is 6% of its markdown. Today search covers titles, prose and keywords; indexing the bodies of code blocks, so that finding a call site costs what finding a sentence does, is the next thing.

$ theourgia link koou2buo.2 implements koou2buo.1
$ theourgia insert --under root --title "Mentions by id" \
    --text "See [[koou2buo.1]] for the reasoning."

$ theourgia refs koou2buo.1
(ok (items (ref (from "koou2buo.2") (rel implements) (via link))
           (ref (from "koou2buo.4") (rel ref) (via md))))

What refs resolves, exactly Measured, because this is easy to over-claim. A mention resolves by id: a block whose text contains [[koou2buo.1]] shows up as (ref (from ...) (rel ref) (via md)). A mention by title does not -- a block written with [[The design]] did not appear in refs for the block titled The design. An explicit edge shows up as (ref (from ...) (rel implements) (via link)) under whatever relation name it was given. So renaming a block leaves explicit edges and id mentions intact, because both are by id; what does not survive a rename is a reference that was only ever a name.
04

Human-agent symbiosis

The store is not only for the automated half. It is meant as a semantic layer that human developers and agents share: the same blocks, the same edges, the same history, whichever side wrote them. For people that means an editor, not a command line.

In the editor today

The store is not only for the automated half. A VS Code extension puts the outline in the sidebar, opens a block as an editor tab, and saves an edit the way any writer does -- into that writer's own space, then committed. It knows when a block has moved underneath an open tab and offers to reconcile it, it keeps saves that could not be delivered and retries them, and it can show what other sessions are holding. It is version 0.0.1.

In the editor, next Two things people ask for that it does not do yet. Edges cannot be edited from the editor: links are made and removed with link and unlink. And the sidebar does not follow somebody else's writing as it happens -- live updates need a change stream the store does not publish yet, so today a refresh is a refresh. Both are planned; neither is here.

The block world inside an IDE, with nothing of IntelliSense lost

Where the extension is going, and the reasoning. None of this is in it yet -- today it shows the outline, opens a block and saves through the writer's own space -- but it is the design the extension is being built toward, and it is the concrete form the shared layer takes. The rule underneath: the block world inside an IDE loses nothing of IntelliSense.

For people

  1. The projection is the editing surface. The extension does not invent a new document type and reimplement completion and go-to-definition. People edit the real files that export-code writes, markers and all, and the language server works natively; on save the extension maps the changed ranges back to block ids by those markers and goes through write and commit. The block world inherits every IDE capability at no cost, and the extension only maps and commits. The markdown side already works this way.
  2. The graph feeds the IDE back. The more valuable direction. Hover and CodeLens providers show, above every definition, what only the store knows: three design sections refer to this, two lessons, last changed by another writer under a named request, see this test. The hover carries the design section's one-line summary. The language server tells you what a thing is; the graph tells you why it is here, who depends on it, and what to read before changing it.
  3. A rename that breaks no link, as a closed loop. An LSP rename produces a workspace edit across files; the extension applies it to the projection and writes it back as one incremental import-code, all of it in one plan, atomically. Block ids do not change, so every edge from a design section, a lesson or a test survives. Then a search for the old name in the prose lists the paragraphs that still use it -- the honest form of exposing documentation that has not caught up.
  4. Reviewing an agent's scratchpad with a full IDE. Each writer's working view projects to a directory of its own, mounted as one root of a multi-root workspace; the language server indexes each agent's draft world separately. Reviewing an agent's change then comes with navigation, types and diagnostics instead of a plain-text diff.

For agents: semantic facts as cheap queries

  1. Diagnostics per block, per writer. The language server's errors and warnings on a projected working view are mapped to block ids and handed to the core as derived data: drafts carries a diagnostic count, and a diagnostics query per writer lists block, severity and message. An agent knows before it commits whether its draft type-checks and whether its names resolve -- verification in the sandbox for languages that do not run here: no running, only asking.
  2. Read-only queries that skip the body. Signatures and types from hover and documentSymbol become derived labels. A read that asks for the signature answers one line, an outline of code blocks lists signatures, and most of the time an agent never needs the body. ctags plus types, as part of the query surface.
  3. Keywords for code blocks, filled in by machine. The write protocol asks for three to eight keywords, which is expensive to write by hand for code. Symbol name, container, kind and type names are exported mechanically as derived keywords, so search recall on code does not depend on a person writing them.
  4. Impact analysis as a traversal. With call hierarchy materialised as calls edges, which tests must rerun when this block changes is one walk of the graph: test block to the block it guards to the transitive calls. Every test hangs off the block it guards; when the block changes, only the related tests run.
  5. External symbols have a place too. Names the store cannot find, such as third-party libraries, come from workspaceSymbol and are answered as external locations, so an agent reading unfamiliar code never leaves the query surface.
05

A zero-conflict concurrent workspace

Several agents and people can write against the same block at the same time. Nothing locks up: each writer's work goes into a space of their own, a scratchpad, and the committed tree stays consistent until somebody commits. A commit that states the version it was based on is checked against the block as it is now; if the base has moved the commit is refused, by name, and handed the content of the writer who got there first -- so the loser has what it needs to merge and commit again, instead of silently overwriting or being silently overwritten.

Scratchpads

Every agent and every person writes under a writer id. The id is what block ids are built from, so a block carries the identity of who wrote it for as long as it exists. One writer id is held by one live agent at a time -- that is a rule in the documentation, not a mechanism in the code; a later session may bind the same id and carry on with its drafts.

write puts a proposed next version of a block into the writing agent's own space. It is not in the log and nobody else can see it. commit, in describe's own words, installs a writer's drafts into the store as one change; the process that owns the store carries commits out one at a time, so the outcome of a race is decided rather than interleaved. With --based-on, the commit states the version the draft was made against. If that premise has moved, the commit is refused.

Baseline optimistic locking

A refused commit does not simply say no. It answers stale-baseline, and it names the version the draft was made against, the version the block carries now, and the records applied since -- the winner's content among them. The agent that lost the race does not have to go and fetch the new state to find out what happened: it already has what it needs to merge and send the commit again.

$ theourgia commit <block> --writer w1

(error stale-baseline
  (block "s9av8p0w.1")
  (based-on "fb580a74...")
  (now "904e0323...")
  (since (("s9av8p0w" . 3)
          (<the record that landed>)
          (set "s9av8p0w.1" src "w2 version")))
  (usage (commit (<block> ...) ("--writer" <name>)
                 ("--working-version" <block>=<version>))))
About that example That answer was taken from a run, not written by hand: two writers took a draft of one block from the same baseline, the second committed, and the first was refused. The two hashes are shortened here to fit the page, and the record in the middle of since is stood in for by a description of it; everything else is as the store answered.

Only if you say what you based it on

--based-on is optional, and leaving it out is not an error. A set or an insert sent without a stated base simply appends: nothing is refused, and nothing is silently dropped, but nothing is checked either, and two writers can end up disagreeing about a field. conflicts is the verb for that -- in describe's words, it lists blocks whose writers disagree. The guarantee above is what --based-on buys; it is not something the store does behind an agent that never asks for it.

Measured under real concurrency

Five agents, five writer ids, one daemon, writing an existing 157-file agent memory (about 430 KB) into one store at the same time: 387 blocks, 0 refusals. An insert of a 3 KB body took 108 ms end to end while that was going on, measured from a source-form client and including the time the client process took to start.

06

A Lisp machine: a living knowledge base

The store is not only somewhere the knowledge is kept; it is a runtime the knowledge runs in. When a block holds Scheme the whole thing is not far from a modern Lisp machine -- with the qualification first: only Scheme blocks evaluate today. Code an agent generated and code a person typed run in place, against the definitions the store holds, in a sandbox, at any point in the log's history.

Evaluation in the block

Only Scheme blocks evaluate today. A library block in datum mode holds one definition per child block, and eval --under <library> evaluates an expression with those definitions in scope. The environment is the R6RS libraries and a small read view of the store; a library that asks for anything else is refused rather than quietly given less. The evaluation is a child process with a wall-clock limit, a memory limit and an output quota, and what it prints comes back in a field of the answer instead of mixed into it.

Evaluate at a point in history

Because the state is a reduction of the log, an evaluation can be asked for at a cut -- and it then runs the definitions as they stood at that point. Not a diff of the source, the behaviour: the old definition, called. The answer always reports the cut it actually used, so the run has a coordinate to be repeated from.

$ theourgia eval --under <library> '(f)'
(ok (values ("second version")) (working-view #f (("koou2buo" . 8))) ...)

$ theourgia eval --under <library> '(f)' --cut '(("koou2buo" . 7))'
(ok (values ("committed")) (working-view #f (("koou2buo" . 7))) ...)

The definition was changed between the two calls. The second asks for the earlier cut and gets the behaviour that was there then.

What the sandbox is given

The limits are arguments, with bounds: --timeout-ms between 1 and 60000, default 3000; --memory-bytes between 1 MiB and 2 GiB, default 256 MiB; --output-bytes between 128 and 1 MiB, default 65536. The output quota counts what the evaluation actually printed rather than what the framing made of it. A run that exceeds one is answered (error eval-limit (resource time|memory|output) (limit <n>) ...) -- which resource, and what the limit was.

Branches side by side: not yet

Evaluating a library against a writer's own uncommitted drafts is not something to lean on yet. --working exists and reports the view it used, but a draft over a definition block does not come into scope: measured, an expression that touches the drafted name fails as though the name had never been defined, while the same expression against the committed state answers. So running a branch in a scratchpad, and running several branches side by side to compare them, is a plan rather than a feature. What works today is evaluation against what is committed, at any cut.

How the numbers were taken Every figure on this site comes from one of two measured runs: 157 files of a real agent memory written by five concurrent agents, and 113 documents converted and then queried. Four things are worth knowing before quoting them. The token counts use cl100k_base, which is OpenAI's tokenizer, not Claude's and not a billing unit; calibrated once against real context growth it ran about 9% low. How much a query saves tracks the size of the block that happens to answer it, not anything theourgia does: in the bucket where the answering block is most of the document the median query still cost 95.2% of reading the whole thing. Small documents have little to give either -- under about a thousand tokens the median was 38.5%, and one README's outline alone came to 67.6% of the document it summarised. And roughly 40% of queries made without knowing what is in the store fall back to reading the outline first.
Start

A store is a directory

# a store is a directory
theourgia init

# one block answers one question
theourgia insert --under root --title "Why the retry is three deep" \
  --keywords "retry, supervisor, worker, timeout" \
  --text "..."

# find it again without reading the store
theourgia search "retry supervisor"
theourgia read <id>

# what is under this block?
theourgia outline --depth 1

theourgia is R6RS Scheme and builds with Chez Scheme against Igropyr. build.ss compiles every library in the tree into a directory of objects; the client, the MCP shell and the sandbox worker are the scripts beside them. There is no package to install and no daemon to configure: point the client at a directory and it starts what it needs.
